# The Evolution of Todo — Phase I (CLI In-Memory Application)

## Core Philosophy
This project is NOT about writing code manually. It is about designing software using specification-driven, AI-assisted development.

ALL code must be generated by AI agents based strictly on approved specifications.

NO boilerplate, NO premature optimization, NO unnecessary abstractions.

## Development Rules (Non-Negotiable)

### I. Spec-First Development
- **Rule**: Never write or generate code without an approved specification. Every feature must start with a clear, structured spec.
- **Rationale**: Ensures that development is always aligned with clear, pre-defined requirements, preventing scope creep and unguided implementation.
- **Enforcement**: Specs must be saved in a `history/specs` folder with versioning.

### II. Agentic Workflow
- **Rule**: Follow this exact workflow: Write Specification → Generate Architecture Plan → Break into Atomic Tasks → Implement Tasks via AI → Review & Refine.
- **Rationale**: Provides a structured, repeatable process for AI-driven development that ensures quality and traceability from spec to code.

### III. No Manual Coding
- **Rule**: Humans MUST NOT write application code (e.g., Python). Only AI-generated code is allowed in the final product.
- **Rationale**: The core experiment of this project is to test the limits of spec-driven AI code generation.
- **Enforcement**: Human role is strictly limited to Product Architect, Reviewer, and Agent Orchestrator.

### IV. Strict Scope Control
- **Rule**: Phase I is strictly a CLI-based application. No database, no file persistence, and no UI/web/API interfaces are permitted.
- **Rationale**: Keeps the initial phase focused on validating the core logic and the agentic development process on a constrained, well-defined problem.
- **Enforcement**: All data structures must be in-memory.

## Functional Requirements

The Todo application MUST support:

- **Add Task**: With a required title and optional description. Default status is 'incomplete'.
- **View Tasks**: List all tasks showing ID, title, description, and a clear status (e.g., [x] or [ ]).
- **Update Task**: Modify the title and/or description of a task, identified by its ID.
- **Delete Task**: Remove a task by its ID, with a confirmation step.
- **Toggle Status**: Mark a task as complete or incomplete by its ID.

## Technical Standards

- **Language**: Python 3.13+
- **Code Style**: PEP 8 compliance is mandatory.
- **Project Structure**: Code MUST be organized as follows:
  ```
  /src
    └── todo/
        ├── __init__.py
        ├── models.py      # Data structures
        ├── service.py     # Business logic
        ├── cli.py         # Command-line interface logic
        └── main.py        # Application entry point
  ```

## Quality Principles

- **Single Responsibility Principle (SRP)**: Each module and function must have one, and only one, reason to change.
- **Separation of Concerns**: Strictly separate data models, business logic, and presentation (CLI) layers.
- **Clarity**: CLI output must be human-readable. Variable and function names must be meaningful and unambiguous.
- **Predictability**: The application must behave consistently and predictably from the user's perspective.

## Deliverables

1.  **Constitution**: This document (`.specify/memory/constitution.md`).
2.  **Specification History**: A `specs_history` folder containing all spec iterations.
3.  **Source Code**: A `/src` folder with the AI-generated Python code.
4.  **README**: A `README.md` file detailing the project, setup instructions using `uv`, and how to run the application.

## AI Behavior Constraints

- **No Assumptions**: Do not invent or assume missing requirements.
- **Clarify First**: Ask clarifying questions during the specification stage, not during implementation.
- **Follow Process**: Never skip the defined agentic workflow steps.
- **Simplicity Over Complexity**: Do not over-engineer. Focus on the simplest, clearest path to correctness.

## Governance

This Constitution supersedes all other practices and documents. All development activities, specifications, and reviews MUST verify compliance with these principles. Any proposed amendment requires documentation, justification, and an approved migration plan.
